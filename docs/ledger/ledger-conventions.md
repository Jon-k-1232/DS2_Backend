## 1. Purpose and UI

DS2 carries a customer's billed debt forward into a new statement. Payments, write-offs, and adjustments change that debt through invoice snapshots. Retainers hold money separately until a draw applies it. The ledger documents are [payments](payments.md), [retainers and prepayments](retainers-and-prepayments.md), [write-offs and adjustments](write-offs-and-adjustments.md), and [pending payments](pending-payments.md). (`src/endpoints/payments/payment-logic.js:471`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:248`.)

## 2. Access rules

All four ledger routers require authentication and `requireManagerOrAdmin`. Its exact allowed roles are `manager`, `admin`, `super admin`, and `owner`, compared in lowercase. A valid token must identify an active user. The cookie is checked first, then a Bearer token. Missing, invalid, expired, or no-longer-valid-user authentication returns HTTP 401; an authenticated user outside the allowed roles gets HTTP 403. (`src/app.js:143`, `src/app.js:145`, `src/app.js:155`, `src/endpoints/auth/jwt-auth.js:7`, `src/endpoints/auth/jwt-auth.js:18`, `src/endpoints/auth/jwt-auth.js:64`, `src/endpoints/auth/jwt-auth.js:94`, `src/endpoints/auth/auth-service.js:26`.)

Every `:accountID` passes through `enforceAccountId`. It must convert to an integer equal to the authenticated user's account. A missing authenticated account returns 401; a malformed or different account returns 403. There is no super-admin account bypass here. The URL `:userID` is a legacy parameter: these routers have no self-or-privileged check on it. Create operations use the authenticated user's ID; body `accountID`, body `loggedByUserID`, and URL `userID` cannot choose the ledger owner or creator. (`src/endpoints/auth/account-scope.js:7`, `src/endpoints/payments/payments-router.js:6`, `src/endpoints/retainer/retainer-router.js:6`, `src/endpoints/writeOffs/writeOffs-router.js:6`, `src/endpoints/pendingPayments/pendingPayments-router.js:16`, `src/endpoints/payments/payment-logic.js:373`.)

The frontend manager gate allows `admin`, `manager`, `super admin` and `owner`, matching backend ledger access. This fixes finding [F37](../_review/findings.md#f37). (`../DS2_Frontend/src/Routes/ManagerAndAdminProtectedAccess.js:9`.)

## 3. API conventions

This file defines shared behavior and owns no endpoint. The four ledger feature guides own 26 contracts: 6 payments, 5 retainers, 5 write-offs and 10 pending payments. The adjustment endpoint belongs to [billing review](../invoicing/billing-review.md). See the complete [endpoint index](../README.md#endpoint-index).

| Shared contract | Exact behavior |
| --- | --- |
| HTTP versus JSON status | Payments, retainers, and write-offs generally send HTTP 200 even when JSON contains `status:404` or `status:500`. Their paginated lists use real HTTP error codes. Pending-payment routes use real HTTP status codes. Do not infer success from HTTP 200 alone. (`src/endpoints/payments/payments-router.js:26`, `src/endpoints/payments/payments-router.js:178`, `src/endpoints/retainer/retainer-router.js:94`, `src/endpoints/writeOffs/writeOffs-router.js:167`, `src/endpoints/pendingPayments/pendingPayments-router.js:27`.) |

Parser failures can return 400 for malformed JSON or 413 for oversize bodies before the router. The final error handler uses `err.status` or 500 and masks the message in production. (`src/app.js:70`, `src/app.js:94`, `src/app.js:120`, `src/app.js:178`.) |
| Pagination | Ledger list routes supply page 1 and limit 20. The shared helper itself defaults to limit 10, as used by timesheets; defaults are route-specific. `parseInt` is used, so `2.9` and `2x` become 2. ## 5. Read logic

### Current debt and statement membership

The normal balance-forward model is **the newest parent statement represents the customer's billed debt**. Do not sum the remaining balances of every historical parent. For mutations, load account/customer roots with null parent, order by invoice date descending then ID descending, keep every root on the newest invoice date, and resolve each root's latest child by `created_at DESC, customer_invoice_id DESC`. Use that child balance, or the parent if no child. Exclude chains whose parent or latest child contains an absorption marker. If all roots on the newest date are absorbed, refuse rather than reopen an older balance. Same-day independent roots are deliberately supported. (`src/endpoints/payments/payment-logic.js:51`, `src/endpoints/payments/payment-logic.js:99`.)

Keep the requested chain if it is live. Otherwise choose the live chain with the largest remaining balance; payment/write-off creation refuses if that remapped target is not positive. The newest-parent lookup used for statement immutability also accepts a legacy self-parent and sorts by invoice date, timestamp, then ID descending. This is a separate query from current-chain selection. (`src/endpoints/payments/payment-logic.js:66`, `src/endpoints/payments/payment-logic.js:179`.)

Billing gets the latest parent marker per customer with `DISTINCT ON`, ordered by invoice date, timestamp, and ID. Payments and write-offs enter the period when their **own** `created_at` is strictly greater than the marker parent's timestamp, compared by PostgreSQL. Payment date and write-off date do not decide this membership. The legacy fallback uses a supplied timestamp, or a date with `>=`; no marker means no cutoff. (`src/endpoints/invoice/invoice-service.js:10`, `src/endpoints/invoice/invoice-service.js:183`, `src/endpoints/invoice/invoice-service.js:288`, `src/endpoints/invoice/invoice-service.js:315`.)

All unbilled transactions (`customer_invoice_id IS NULL`) are fetched regardless of work date, joining jobs and job types. Payments join invoice number; write-offs join linked invoice/root and job information. Retainers are fetched without a billing-date cutoff, ordered by database creation timestamp then ID, and also select an exact timestamp text value for in-memory comparison. These arrays are grouped by customer in memory. (`src/endpoints/invoice/invoice-service.js:263`, `src/endpoints/invoice/invoice-service.js:288`, `src/endpoints/invoice/invoice-service.js:315`, `src/endpoints/invoice/invoice-service.js:349`.)

Outstanding-invoice preparation selects roots by account, selected customer IDs and null parent, ordered by creation timestamp/ID descending. It separately fetches children whose parent ID is in that root set, with the same descending order; that child query does not repeat the account filter. It groups children by root in memory. (`src/endpoints/invoice/invoice-service.js:377`.)

For each root: skip an invoice date earlier than the customer's last bill date; include a positive parent without children; otherwise skip the whole group if its latest child is both zero and paid. If any child is positive, include children followed by parent. Otherwise include that same sequence if the parent creation timestamp is at/after the last bill date, or a zero child was created after that date. Those last checks compare timestamps to the bill date, not the exact statement marker used for period payments. (`src/endpoints/invoice/invoice-service.js:417`.)

The outstanding calculator groups this sequence by invoice number. A row with paid flag, paid date, or zero remaining discards its whole number-group unless a period payment matches its invoice number or a period write-off matches its row ID. Eligible balances must be positive and have invoice date at/before the last bill date. Among the same number, replace a candidate only with a later invoice date; equal-date ties retain the first encountered row. Finally remove discarded groups and sum remaining balances. This is why summing all snapshot rows is incorrect. (`src/endpoints/invoice/createInvoice/invoiceCalculations/outstandingInvoicesCalculations.js:3`, `src/endpoints/invoice/createInvoice/invoiceCalculations/outstandingInvoicesCalculations.js:48`.)

### Other views

The account invoice list inner-joins customers and creators, scopes on invoice account, and orders by invoice date descending. Lists and grids may contain parent and child history together. (`src/endpoints/invoice/invoice-service.js:31`.)

Accounts receivable selects newest-date roots, resolves each latest child with a lateral query ordered by timestamp/ID, groups by customer and statement date, and sums `GREATEST(remaining,0)`; only positive customer sums remain. Its aging uses `EXTRACT(DAY FROM (NOW()-statement_date))::int`: 0–30, 31–60, 61–90, and over 90 days. Future dates also satisfy the first `<=30` bucket. Each customer's whole billed balance goes into the bucket for that statement date. (`src/endpoints/accountsReceivable/accounts-receivable-service.js:80`.)

The optional oldest-charge estimate selects positive billed billable transactions, orders by transaction date/ID descending, and forms a running sum including each charge and all newer charges. A charge remains partly unpaid under this estimate when `runningSum-chargeAmount < customerOutstanding`. Take the minimum date among those charges. This is a FIFO estimate, not stored allocation of each receipt. (`src/endpoints/accountsReceivable/accounts-receivable-service.js:167`.)

## 6. Calculations

1. Shared payment/retainer/write-off cores use `round2(n) = Math.round((Number(n) + Number.EPSILON) * 100) / 100`. This is JavaScript floating-point rounding, not an arbitrary-precision decimal implementation. Billing-review adjustments have a separate symmetric rounding helper; see the adjustment document. (`src/endpoints/payments/ledger-helpers.js:11`, `src/endpoints/billingReview/cascadeEdit.js:83`.)
2. A normal payment or write-off stores `-round2(abs(input))`. A snapshot's new remaining balance is old remaining plus that signed amount. A positive reversal adds debt. The parent mirrors remaining balance, signed payment/write-off totals, and paid flags. It does not recompute total charges or original total due for a receipt. (`src/endpoints/payments/payment-logic.js:77`, `src/endpoints/payments/payment-logic.js:260`, `src/endpoints/writeOffs/writeOffs-logic.js:75`.)
3. Billing's payment contribution is the sum of period payments **without** an invoice link. Invoice-linked payments have already moved the outstanding snapshot. A separate payments-received total includes all period payment rows for display. Retainer/prepayment payment totals require an uninvoiced payment whose method is exactly `Retainer` or `Prepayment`. (`src/endpoints/invoice/createInvoice/invoiceCalculations/paymentsCalculations.js:6`.)
4. Current-chain invoice write-offs also already moved outstanding balance and are not deducted again. Older absorbed-chain write-offs may contribute a period credit. Job/general credits contribute to the write-off line when shown, or reduce job totals when hidden. Invoice-linked credits are excluded before hidden job grouping, including when they share a job with new work ([F8](../_review/findings.md#f8), fixed). (`src/endpoints/invoice/createInvoice/invoiceCalculations/writeOffCalculations.js:23`, `src/endpoints/invoice/createInvoice/invoiceCalculations/transactionCalculations.js:52`.)
5. `amountDue = outstandingBalance + transactionTotal + paymentTotal + writeOffTotal`. `amountDueBeforeRetainers = amountDue - retainerPaymentTotal`. Remaining retainer is shown separately and is **not** automatically subtracted again. Retainer display sums only the latest row of each chain that is active and nonzero. (`src/endpoints/invoice/createInvoice/invoiceCalculations/totalInvoice.js:4`, `src/endpoints/invoice/createInvoice/invoiceCalculations/retainerCalculations.js:33`.)
6. Example: old debt $500, applied receipt -$120, applied invoice write-off -$30, new unbilled work $200, and an uninvoiced retainer-funded payment -$40 produce $350 outstanding and $510 due (`350 + 200 - 40`). The received-payment display includes the $120 and $40; it is not another $160 subtraction. This follows the preceding calculators. (`src/endpoints/invoice/createInvoice/invoiceCalculations/paymentsCalculations.js:6`, `src/endpoints/invoice/createInvoice/invoiceCalculations/totalInvoice.js:4`.)
7. Six-minute rounding belongs to time charges, not receipt amounts. In automatic timesheet ingestion: `quantityHundredths = ceil(minutes/6)*10`; `rateCents = round(rate*100)`; `totalCents = round(quantityHundredths*rateCents/100)`. Quantity is hundredths/100 and total is cents/100. Thus 68 minutes becomes 1.2 hours; at $137.50/hour it is $165.00. (`src/endpoints/timesheets/auto-ingest-orchestrator.js:541`.)

## 7. Create, edit, delete, locks, and audit trail

Manual payment, retainer, and write-off cores run inside one transaction; a passed-in transaction is reused. They lock the owning `customers` row with `FOR NO KEY UPDATE`, scoped by account. For edits/deletes, the owner comes from the stored ledger row. This serializes participating writers for that customer. It does not make unrelated code or the nontransactional pending soft-delete path atomic. (`src/endpoints/payments/ledger-helpers.js:21`, `src/endpoints/payments/ledger-helpers.js:62`, `src/endpoints/payments/ledger-helpers.js:75`, `src/endpoints/pendingPayments/pendingPayments-router.js:112`.)

Use `clock_timestamp()` after acquiring the lock for new ledger rows. Transaction-start `now()` could place a writer that waited for billing before the statement timestamp. Billed-data checks remain inside PostgreSQL to preserve submillisecond precision: an event at or before the newest parent is billed. Payments/write-offs use their linked invoice snapshot as the event anchor, falling back to their own row if no snapshot exists. Retainer draw movement has its own billed-row check. (`src/endpoints/payments/ledger-helpers.js:30`, `src/endpoints/payments/ledger-helpers.js:119`, `src/endpoints/payments/payment-logic.js:201`, `src/endpoints/payments/payment-logic.js:226`, `src/endpoints/writeOffs/writeOffs-logic.js:36`.)

The billed helper returns false with no valid newest-parent ID, no matched SQL row, or a null timestamp comparison (`COALESCE(...,false)`). It does not infer a historical billing event from amount, entered date, or note alone. (`src/endpoints/payments/ledger-helpers.js:119`, `src/endpoints/payments/ledger-helpers.js:143`.)

A payment/write-off snapshot clones the latest invoice row, removes its ID, joined address fields, and creation timestamp, and sets root parent, remaining balance, paid flag, and paid date. Copied invoice totals, creator and notes are otherwise inherited; the parent mirror receives the signed total change separately. A child is a balance event, not a separately issued new invoice or a recomputed full statement. The paid flag is true only at rounded zero; reopening sets paid date to null. (`src/endpoints/payments/payment-logic.js:77`, `src/endpoints/payments/payment-logic.js:316`.)

Amount edits and deletes require the affected invoice child to be newest in its chain. Metadata-only payment/write-off edits can leave an older unbilled child's amounts alone. Billed rows are refused; NSF uses a new positive event on the current chain. Direct retainer edits differ: they shift every chain balance by a starting-amount delta and do not apply this statement immutability gate. See the feature documents for exact refusals. (`src/endpoints/payments/payment-logic.js:820`, `src/endpoints/payments/payment-logic.js:893`, `src/endpoints/payments/payment-logic.js:1012`, `src/endpoints/retainer/retainer-logic.js:85`, `src/endpoints/writeOffs/writeOffs-logic.js:143`.)

Billing first reads pricing inputs and a ledger fingerprint in one read-only repeatable-read snapshot. Finalization builds PDFs/ZIPs, then locks the account and customers in sorted order, rechecks duplicate/same-day rules and fingerprint, inserts a new parent, absorbs the exact carried chains, and stamps listed unbilled transactions/payments with the invoice ID. It checks affected row counts. It does not stamp write-off or retainer rows; their timestamp/chain rules determine later membership. (`src/endpoints/invoice/createInvoice/billingSnapshot.js:27`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:46`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:70`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:200`.)

Absorption zeroes every row in each carried chain and appends the destination marker. Historical flags and charge totals can remain. New statement balances retain the signed ledger totals, and zero total due marks the new parent paid. Export keys contain a run ID and customer ID. S3 export generation precedes the database transaction; it is not a cross-service atomic commit. Manual payment/retainer/write-off cores themselves make no S3 or notification call. (`src/endpoints/invoice/invoice-service.js:509`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:225`, `src/endpoints/invoice/invoiceDataInsertions/dataInsertionOrchestrator.js:248`, `src/endpoints/payments/payment-logic.js:428`, `src/endpoints/retainer/retainer-logic.js:55`, `src/endpoints/writeOffs/writeOffs-logic.js:75`.)

Audit evidence consists of creator/timestamps, snapshots and notes, plus billing-review correction records for cascade edits. Ordinary updates preserve the original creator and usually mutate the existing row; accepted deletes remove ledger rows. This is not a universal append-only journal. Mutations refresh display tables after the transaction commits, so a refresh failure can report an error after the money movement committed. (`src/endpoints/payments/payment-logic.js:273`, `src/endpoints/payments/payment-logic.js:820`, `src/endpoints/payments/payment-logic.js:976`, `src/endpoints/billingReview/cascadeEdit.js:676`.)

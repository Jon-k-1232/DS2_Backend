# Performance: bounded loading and account-wide calculations

The workspace loads small reference data once per account/user/role. Jobs are fetched only for the current screen or selected client. Financial calculations, sent locks, business attribution, audit writes and adjustment permissions remain server responsibilities.

## Loading contracts

- `initialBlob` keeps its twelve shell keys for compatibility, with an empty `accountJobsList.activeJobData.activeJobs`. It sends no `grid` or `treeGrid`. Transactions, invoices, payments, write-offs and retainers are limited to the first 20 rows. Users and the small category/type/description/recurring catalogs remain reference lists.
- Active customer identities include only customer/account ID, display/customer/business name, recurring and active flags. Up to **1,000 active clients**, the whole compact directory is loaded once for instant local picking. Above 1,000, the directory is empty with `remote:true`, `totalCount` and `threshold:1000`; pickers search the server with a 200 ms debounce and a maximum 50 choices per search. The API also supports bounded paging and lookup of an exact selected ID, including inactive records needed by historical edits.
- Job choices use `/jobs/getActiveCustomerJobs/A/U/C?search=...&limit=100&entityId=...`. The latest version of each family is selected in SQL before paging; completion status remains visible and is not an implicit filter. A selected historical ID is separately hydrated with its job/type/category labels and rate. Switching client/business aborts obsolete requests and clears invalid selections. Legacy shared jobs remain eligible for the explicitly chosen business.
- Jobs and retainers have independent server-paged registers (20 rows initially, API maximum 100), search, business filters, visible errors and retry. Jobs also have allowlisted server sorting with an ID tie-breaker. Their reads never overwrite shared context. Mutation revisions invalidate registers once, without a duplicate fetch when bootstrap references arrive. Client/job names lead the grid columns; internal IDs do not push them offscreen. Job search covers client, type, category, notes and exact job ID. Retainer search covers client, hold label, payment reference and note. Register export/print menus explicitly say “this page”; they export the loaded page rather than implying an account-wide export. The retainer register presents root and draw snapshots as separate history rows; per-client trees remain available in the client profile. Client job trees still load only within that selected profile.
- Stable record URLs fetch the selected job/retainer/client directly, so editing or deleting a record outside page 1 works. Job deletion checks the whole family, with counts and up to 100 linked rows per kind. Catalog deletion loads a bounded dependency preview by category/type rather than consuming every job in the account.

The write-off job picker adds `currentCycle=true` to the existing per-client endpoint. It searches/pages exact referenced job versions and preserves the former amount rule: sum only billable work without an invoice or retainer, grouped by exact job ID. Zero-valued historical groups remain selectable; IDs disambiguate identical descriptions. Lifetime `current_job_total` is never substituted for this amount. Client/business changes invalidate old choices. The current-cycle aggregate uses account-qualified unique-key joins with the exact `ds2_effective_entity` precedence: explicit entity, amended legacy billing scope, original attribution, then reviewed resolution. Read-only legacy equivalence tests compare both the rows and amounts with the existing scoped view.

Legacy payment and write-off invoice selectors request `GET /customer/activeCustomers/customerByID/A/U/C?section=invoices&entityId=E`. This projection returns only that client's invoice snapshots in `customerInvoiceData`, preserving current-chain/absorption selection rules without downloading jobs, work, payments or retainers. It rejects malformed sections and missing/foreign clients, retains existing role/business guards, and performs no writes. Full client-profile/history views remain unchanged. Late responses cannot reset an invoice/job or overwrite the new client's choices.

## Mutation responses

`committedResponse` preserves the existing saved/reload/do-not-resubmit contract. Successful customer, job, transaction, payment, write-off and retainer mutations return `committed:true`, `changed` identities/records, and only the refreshed first page (20 rows) of affected registers. Deletes identify removed IDs. Customer edits include only that client's recurring-plan records. No account-wide job/payment/customer/retainer/write-off list is returned. A refresh or changed-row hydration failure after commit returns committed success with a visible warning; the operator must reload, never resubmit that write.

`listViews.js` derives grid and tree views in the browser on demand using non-enumerable getters. The wire has one row representation. `mergeWorkspace` patches changed customer identities into the small reference directory, removes deactivated/deleted clients, and switches to remote mode when it crosses the threshold. A page of customer search results or a scoped record lookup never replaces the directory. Financial registers invalidate their own reads on a successful save; filters and page state remain local.

## Route delivery

Workspace pages and record groups use `React.lazy` with one accessible Suspense loading state (`RouteLoading`). Route imports are statically discoverable by the bundler. After authentication and a successful bootstrap, an idle callback prefetches Enter time/Transactions and Create invoices for permitted roles; a two-second timer is the fallback. Other routes are fetched when visited. Router transitions retain the mounted outgoing page while a new chunk loads, avoiding a virtual-grid scroll callback against hidden/unmounted DOM. The first route may share framework/vendor chunks with later screens; prefetch is intentionally additional idle traffic, not required startup traffic.

## Database and budgets

Migration **047** adds client/family job indexes, the compact client directory index, and account/date and account/client retainer indexes. It contains only idempotent index DDL and changes no business/audit rows. The bounded jobs query uses the equivalent jobs-view predicate on `public.customer_jobs`: account ownership plus raw shared (`NULL`) or selected-business rows. An explicit stored entity always wins in `ds2_effective_entity`; shared jobs remain admitted by the existing view rule. Effective attribution is projected only for returned rows, after latest-family selection/paging. This avoids resolving attribution on every historical version. Existing route guards and the business/client refusal matrix remain authoritative. Other entity reads retain their existing views. Read-only `EXPLAIN (ANALYZE, BUFFERS)` and payload evidence live in [H9 results](../decisions/2026-09-26-run-H9-results.md).

Executable budgets use account-1-scale data without writes: initial JSON <1,000,000 bytes; each of the three largest job histories has a warm seven-sample median <50 ms (one warmup), both without a business filter and with the default business, for normal and current-cycle choices (12 cases), and each response has <=100 jobs. Browser tests check the four primary pages under 12 seconds, server paging/retry, real client/job type-ahead and stale client reset. Local browser times include development compilation/network-idle delay; they are a repeatable local usability proxy, not a production Web Vitals certification. Timing samples are taken with one test process at a time.

The [H9 scenario oracle](../scenarios/H9-bounded-loading.md) connects compact responses to unchanged money outcomes and refusal/no-write assertions. Full regression remains required because entry, review, recurring, record and delete screens share these selectors.


H9 also applies the profile projection to active payment record editors and pending-payment review (`section=invoices`). Editors hydrate their exact selected job and retainer separately. Retainer deletion uses `section=payments` to check the complete client payment history, including links outside any grid page, without fetching jobs or work. Retainer credit transfer uses `section=retainers`; all business balances remain available for choosing the source. These projections retain the existing manager/admin read guards, selected-business behavior and failure recovery. The actual client profile still loads its full per-client history/tree views.

Client/business changes clear both the visible job text and its search query, including switching away and back. This applies to entry forms, current-cycle write-offs, recurring plans and inline billing review. An obsolete response cannot restore choices from the earlier scope.

Inline processed-work review uses the shared client type-ahead in both directory modes. The selected client identity also seeds inline job creation. Job choices use the transaction business; changing client clears the old job and search, requires a new job, and preserves entered work through lookup or save failures. The H9 browser oracle moves one $22.50 transaction between two fixture clients after proving both refusal paths leave them unchanged.

## H10: account-wide calculations

Invoice supplementary evidence is batched per table/customer set; eligibility fetches only the work columns it consumes. Migrations 048/049 replace repeated entity-function reads in the work/job views with equivalent unique-key joins. AR has a batch reporting projection that omits unused command fingerprints. Analytics uses narrower evidence encoding and request-local customer/document indexes; the year-end packet prepares one snapshot for its four reporting worksheets. There is no application cache or invalidation dependency.

The original invoice math, issued locks, finalize fingerprint, audit attribution and independent Audit/AR reconciliation are unchanged. Account-1 source rows are read-only, while scenarios and browser writes remain isolated to their authorized fixtures. The [H10 results](../decisions/2026-09-26-run-H10-results.md) contain before/after API and phase tables, query counts, EXPLAIN plans, browser budgets, protected hashes and full regression counts.

Executable H10 budgets use one warmup plus three measured samples at real account-1 scale: Create invoices first rows ≤1 second/all balances ≤1.5 seconds, AR ≤1 second, Audit list ≤1.5 seconds, and each of six analytics pages ≤2 seconds. Browser readiness means actual data or the legitimate empty result, not a shell or network-idle event. Browser navigation starts within a loaded workspace; cold document startup is separately retained. The only substituted request on account 1 is the preparation POST, answered from the real read-only due preview so no fee is generated. API budgets include the full response body. A missing account-scale dataset is the sole permitted budget skip.

Original readers are frozen under `test/fixtures/h10-baseline` with SHA-256 checks. Ordered public AR/analytics reports are byte-identical; complete invoice inputs/calculations are compared as canonical JSON, preserving every value/type/record while normalizing unordered SQL row sets and object keys. The old readers have no ORDER BY on some invoice input sets and do not themselves guarantee byte order under parallel query execution. Separate checks compare every new view row against the original attribution function. Every money oracle and drift check remains required.

## H8 browser continuation

H8 retains H9's bounded bootstrap, per-client job/client lookups and lazy route coverage, and H10's real-data loading budgets. Correction controls additionally wait for all required balance reads. Delayed grid reads respect keyboard focus. The H8 acceptance contains two complete Chromium runs without retries, including the unchanged H9/H10 budgets; their H8 measurements are retained separately from earlier-run evidence.

# Audit Record: deterministic customer history

Owner decision 6 is implemented separately from the existing AI Audit reconciliation. No model supplies this record, its balances, attribution, verification or PDF. The client profile's **Audit Record** tab is available to **Admin and Super Admin only**. Managers, legacy Owners and ordinary users cannot see the tab or call its API. `AuditRecordProtectedAccess.js` documents the guard; the backend independently checks the role and account. Super Admin never bypasses tenant scope.

Draft invoices remain editable and write nothing to the ledger. **Finalize means sent and locked.** The existing narrow bounced-check exception permits a compensating reversal, not edits to the original issued evidence.

## Capture and existing evidence

Migration 026 adds `audit_events`, `audit_chain_heads`, `audit_policy`, `audit_records` and `audit_actions`. It retains migration 019 normalization evidence, 023 invoice membership/history/revisions, 024 retainer/duplicate evidence, and 025 credit-selection reasons. It updates no historical business rows. The activation timestamp survives reruns; capture becomes effective when the migration commits.

Row triggers capture INSERT, UPDATE (including no-op updates) and DELETE on:

| Area | Tables |
|---|---|
| Customer/work | customers, customer_information, recurring_customers, customer_rate_agreements, customer_jobs, customer_quotes, customer_transactions |
| Catalog/rates | customer_job_types, customer_job_categories, customer_general_work_descriptions, users, accounts, account_information |
| Cash/credit | customer_payments, customer_writeoffs, customer_retainers_and_prepayments, retainer_events |
| Issuance | customer_invoices, invoice_issues, invoice_statement_members, invoice_exceptions, invoice_exception_payments, invoice_revisions, invoice_history |
| Duplicate review | duplicate_flags, duplicate_history |
| Imports | timesheet_entries, ai_time_tracker_transaction_suggestions, ai_category_training_examples, customer_payments_processed |
| Maintenance/printing | ledger_normalization_log, audit_records, audit_actions |

Each event retains UTC time, actor ID and name at write time, account/customer and previous customer, entity/key, action, full before/after values, changed fields, reason/note, source, transaction ID, and correlation ID. Names are copied into the event, never joined later to rewrite attribution. `created_by_user_id` and `logged_for_user_id` remain business provenance; neither is inferred to be the acting user for a new event.

`src/utils/auditContext.js` uses AsyncLocalStorage at the authenticated HTTP request boundary and Knex's PostgreSQL query boundary. Every transaction gets transaction-local settings; standalone legacy writes get their own atomic context/write transaction. The actor is the authenticated session, even if URL/body user IDs differ. `SET TRANSACTION` runs before context queries, preserving the billing snapshot's isolation. Automatic tracker ingestion runs as system with `automation/tracker-ingestion` source and the originating request correlation. Direct SQL and image-import writes still trigger capture as system, identifying database application/session/table source. Scripts should set PostgreSQL `application_name` to their script/import name for more specific provenance. Existing `ds2.reason` feature context takes precedence over generic notes.

All events are in the same transaction as their source changes: validation failures, refused sent edits and rollbacks create no committed audit events. TRUNCATE of audited tables is refused. Tenant ownership cannot be changed by UPDATE; a reviewed transfer needs explicitly scoped delete/insert operations. Customer moves within a tenant preserve both customer IDs. Customer deletion cannot cascade away this evidence.

Scripts that combine explicit row locks with writes must acquire `pg_advisory_xact_lock(260026, account_id)` first, matching application lock order. For a multi-account maintenance transaction, acquire these locks in ascending account order before business locks. The trigger still captures writes that omit this convention, but mixed lock orders can cause PostgreSQL to abort a deadlock participant. Acting-user deletion uses the deleted row's name or the authenticated session's name snapshot for subsequent cascade events, so removing a user cannot erase their attribution.

## History and balances

The service reads current rows, events, policy and chain verification in a repeatable-read snapshot. It reverses captured mutations to obtain the pre-logging baseline, including deleted and reassigned rows, then replays committed transactions. Earlier records are explicitly marked **reconstructed from existing records, before audit logging began**. Available creator IDs/dates are retained; historical names and edits that were never recorded stay unknown. Existing invoice/duplicate/normalization histories are included instead of being replaced.

Each history entry groups one database transaction and displays its money activities and field changes. Running balance is calculated **after the complete transaction**, never halfway through a payment/snapshot/finalize cascade. It uses the existing deterministic `auditCustomerLedger` arithmetic: latest live rolling statement balances plus unbilled billable work and pending signed credits, valued through the current billing date. Billed and unbilled components remain separate; AR agrees with the billed component and Create Invoice/Account Audit with the total. Invoice totals are informational issuance markers, not another debit. Retainer receipts/refunds/adjustments affect available credit; draws use their actual payment and are never deducted twice. Billing Review changes and deletes appear as signed changes and retain before-images.

Filtering uses inclusive **America/Phoenix posting dates**, not editable transaction effective dates. Earlier postings establish the opening balance. Pagination slices complete postings without resetting balances. The current position is shown separately from the selected range's closing balance. Pre-logging entries are a reconstruction of surviving evidence, not proof of the balance or user edits as they actually happened at every historical moment.

## API contract

Base: `/auditRecord/customer/:customerID/:accountID/:userID`. Every route requires an active authenticated Admin or Super Admin and a matching session account. `userID` is a positive int32 path parameter; it is not used for actor attribution.

| Method | Suffix | Contract |
|---|---|---|
| GET | (base) | `startDate`, `endDate` real YYYY-MM-DD dates, optional; `limit` 1–100, default25; `offset` 0–2147483647, default0. Returns customer, activation/timezone/methodology, opening/closing/current balances, verified chain anchor, total posting count, whole-range coverage counts and entries with raw changes plus their shared human `presentation`. Reference labels use captured name history at posting time; historical actor names are never inferred from today's user names. |
| GET | `/verify` | Verifies the entire account chain after checking customer ownership. Returns verification status, checked count and anchor, or failed event ID. No other customers' event content is exposed. |
| GET | `/records` | Paginated immutable record metadata for this customer. Returns total, generator ID/name/time, selected range, UUID, full-file and embedded-digest SHA-256, byte length, chain anchor, `record_type` and evidence SHA-256/byte length; neither storage key is exposed. |
| POST | `/records` | JSON object with optional `startDate`/`endDate` and `recordType` (`client`, default, or `full_evidence`). Generates the entire selected range regardless of UI page, stores a new immutable PDF and returns **201** with metadata. Explicit printing creates a new record; reopening uses its ID. |
| GET | `/records/:recordID/evidence` | Returns exact archived UTF-8 JSON after identity, SHA-256, byte length, account chain and retained anchor verification, with `X-Evidence-SHA256`. Read-only; private/no-store. Legacy records without an archive return 404. |
| GET | `/records/:recordID/pdf` | Retrieves exact stored bytes, verifies both document digests, records a nonfinancial reopen action, then returns private/no-store PDF and `X-Document-SHA256`. Never rerenders it. |
| GET | `/records/:recordID/verify` | Returns document/chain/anchor validity, expected and actual full-file hashes, embedded digest, record type and source-archive validity/hash (null for legacy PDFs). Corruption is reported as `valid:false`, not silently ignored. |

Errors: 400 malformed ID/date/range/pagination/record type; 401 unauthenticated; 403 insufficient role or wrong account; 404 missing/foreign customer/record; 409 failed chain on history/new print, corrupted stored PDF, or failed evidence identity/digest/chain/anchor on evidence download; 500 database/storage/render/metadata failure. Failed requests write no financial data or metadata; a failed post-upload DB insert can leave an **unreferenced unique object**. A read of an existing customer's history performs no write. Customer deletion retains history and printable records, retrievable by their customer/record identity through the API.

## Integrity and printing

Database guards refuse log UPDATE/DELETE/TRUNCATE and direct log INSERT. Each account's writes serialize using a transaction advisory lock. The central request transaction boundary takes this lock before business-row locks, preventing employee-deletion/work-insert deadlocks; explicitly read-only snapshots stay nonblocking. Savepoint rollback invalidates the cached lock state so the next query reacquires it before business work. Capture triggers take the same lock for direct SQL writes. Every SHA-256 covers canonical PostgreSQL JSON of all event columns except its own hash, including the previous hash. `ds2_verify_audit(account_id)` checks every event and the head/count, detecting modified content, removed interior events and removed tails. Immutable metadata retains the anchor used to generate each record.

## Client and full evidence presentation (runs 5–6)

The tab defaults to **Client record**, with **Full evidence record** as the other print option. Record type is part of immutable metadata, the PDF title and the printed-record list. Existing PDFs are classified as full evidence without rerendering or changing their bytes. Migration **027.audit_record_presentations.sql** adds record type, evidence key/hash/length and their validation constraints; no business rows or audit events change. Both new print types use the same immutable storage and digest protocol.

`audit-record-presentation.js` supplies identical business descriptions, human field names and formatted amounts to the tab and PDFs. The ledger has one row per complete transaction, describing work/rate/quantity, receipts/check numbers, write-offs/reasons, retainer receipt/application/refund/adjustment, finalized invoice/amount due, bounced reversal or duplicate review/removal. Actor names are those captured at posting. Work charged and the associated retainer draw share a row with separate debit/credit magnitudes. Invoice totals do not add another debit. The existing balance replay and six-minute/explicit-quantity calculations are unchanged.

All USD amounts use `$1,234.56`; negative debt/credit values use `-$1,234.56`. Debit and Credit columns contain positive magnitudes. Retainer availability and original deposit amounts are shown as positive funds in the client view; full evidence retains stored negative credit values. Headings and values use identical right-aligned column positions. Opening, selected closing and current billed/unbilled/retainer positions remain separate.

The client change log groups every captured row change by its database transaction, names the actor and human record, and formats changed fields as before -> after. Creations/removals list meaningful values once. Row IDs, timestamp maintenance, storage paths/slugs, request correlations, renderer/snapshot bodies and ingestion implementation fields are omitted. Invoice assignment becomes a human invoice-number change; known bookkeeping markers become explanations. Invoice PDF archives show the source-snapshot hash when no original-file digest was captured. An unknown historic name is explicitly unavailable. The source archive retains every omitted field. Changes with no visible business fields still have a human entry; no-op updates are identified as such.

Run 6 collapses newly archived statement copies into **one client summary per posting/invoice/revision**, shared by the PDF and tab. Each line names the invoice and action, gives the total and counts by invoice balance, work item, payment, write-off, retainer record and retainer adjustment, states exactly how many captured changes it covers and their change numbers, and points to itemization in full evidence. Other kinds are counted as other statement items rather than dropped. Copies added by a bounced-check reversal stay in that reversal's posting; they are not called a new finalization. Reconstructed copies are labelled reconstructed, not captured. Unknown invoice numbers stay unknown. Unusual updates/deletes or copies without an invoice identity remain individual entries. A revision with no newly captured copies creates no invented archive summary.

Coverage counts include postings, captured/reconstructed changes, raw field changes, human fields and supporting fields. Each event's itemized `presentation.changes` retains its manifest of every source field and its shown/omitted disposition. The additional `presentation.client_changes` supplies individual entries or archive summaries, each with `covered_event_ids`, `covered_change_numbers` and `change_count`. The original events and itemized presentation remain intact. Counts add `client_lines`, `archive_summaries`, `summarized_changes`, `client_human_fields` and `client_supporting_fields`; the client field totals classify all summarized-copy fields as retained supporting evidence. The PDF header still counts **all** captured changes and reconciles individually listed changes plus summarized changes. The tab's Changes count likewise remains the source-change count. Selected-range counts cover the entire range, independently of UI pagination. Completeness compares the union of individual/summary IDs and numbers to database evidence exactly once, checks summary category totals, then reconciles the extracted PDF's individual headings and covered counts to the same captured total.

Full evidence prints human field changes compactly, retaining actual actor IDs, sources, request/transaction identity, signed per-change debit/credit/retainer effects and informational invoice totals. Small scalar technical values remain explicit; their field names are humanized. Structured values and text over 180 characters are replaced by their type, UTF-8 JSON-encoded byte length, SHA-256 and an exact JSON Pointer. Retrieve the archive from the authenticated evidence API printed in the document, follow that pointer and calculate `SHA256(Buffer.from(JSON.stringify(value), 'utf8'))`. Key order is the archive's order. Binary objects use their complete JSON representation for this descriptor; no payload is truncated. All source before/after rows, actors, reasons, UTC times, raw field changes, correlations, event hashes and reconstruction data are retained in the archive even when a compact field print lists only the creation/deletion side.

Each print conditionally creates `audit-records/<account>/<customer>/<uuid>.evidence.json` and its PDF. The archive contains version, generation metadata and the exact selected history from the same repeatable-read snapshot. Its exact digest and byte length live in the guarded record row; the archive digest is also printed in both PDFs. Evidence download checks its deterministic key, bytes, account chain and retained anchor before returning bytes. Verification checks both files. Existing run-4 PDFs remain verifiable with `evidence_valid:null`; no unverifiable source archive is retroactively fabricated. Failures publish no record metadata or financial writes; a storage/metadata failure may leave an unreferenced unique object. Normal downloads never rewrite or regenerate either object.

Both PDFs retain firm/customer/range/generator/Phoenix time, reconstruction notice, finalize=sent sentence, closing position, record UUID, chain anchor and digest explanation. Large record values flow onto subsequent pages.

The client PDF now explains verification in plain language: give the firm the record ID; its system recomputes the SHA-256 digest and checks it against the stored original and audit chain, and can reopen the exact saved document. Matching instructions appear above Printed records in the tab. The client PDF retains the document digest, chain anchor and source-archive digest without an API path or endpoint instruction. Full evidence keeps its itemized statement copies, verified API retrieval paths and JSON Pointers unchanged. Run 6 changes only presentation and tests/documentation: no migration, route, capture, hash protocol, storage, lock, balance or pricing change. Previously stored PDFs/archives retain their original bytes.

Storage keys are unique `audit-records/<account>/<customer>/<uuid>.pdf` with conditional `If-None-Match: *` creation. The private prefix is outside all general invoice-download prefixes. Immutable metadata records the exact final byte count and full-file SHA-256. Reprints return identical bytes even after profile changes or later postings. Creation first takes a read-only consistent snapshot, then renders/uploads it and records metadata in a normal transaction, allowing concurrent ledger writes without corrupting its earlier anchor.

A file cannot practicably contain its own literal full-file SHA-256. The PDF footer explicitly specifies the **digest-field-zeroed** calculation: the fixed-width hex-encoded 64-character digest field is replaced with zero characters before SHA-256. The row/screen/API separately retain the **full final-file SHA-256**. Verification checks both; it never mislabels the embedded hash as a literal full-file hash. A record-specific digest marker distinguishes this field from the all-zero genesis anchor, so a pre-logging account can print its first record.

These controls do not prevent a database owner/superuser from disabling triggers and rewriting all evidence. Production runtime credentials must be non-owner, non-superuser, without replication/DDL rights. Keep backups and exported anchor/document hashes outside that credential's control; enforce object retention and denial of overwrite/delete on the audit prefix. Only a separately authorized operator performs rollout. Local tests use PostgreSQL127.0.0.1:5433 and MinIO127.0.0.1:9000.

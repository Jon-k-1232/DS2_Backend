## Shared rules and issuance boundary

The application has no explicit sent/emailed/mailed state. Draft generation does not persist an invoice; month-end **finalize issues the invoice**, saves its artifact and commits its parent and stamped records. That commit is the definition of **Sent — locked**. It does not claim that an email was delivered. A revision is issued by the explicit resend/reprint choice, with a new immutable artifact; physical delivery remains the operator's action.

**Owner confirmation, 2026-09-25 (verbatim):** "On the sent thats the exact logic i wanted, no change needed. So draft is still editable, and once the invoice is finalized thats basically the same as sent." This rule is settled: a **draft** is not sent and stays fully editable; **finalizing** an invoice is the same as sending it, and from that commit the invoice and every record on it are locked.

Persisted historical parent statements with an artifact are also treated as sent, without rewriting their existing rows. Legacy rows lacking an artifact are not evidence of issuance. Historical metadata is derived conservatively at read/check time; no account-1 data backfill is run in the sandbox. A production archival/backfill review must identify any issued historical statements lacking artifacts before rollout.

Money stays in signed decimal dollars and uses the existing cent-rounding helpers. Receipts and write-offs reduce debt; a payment reversal is positive. A retainer is a negative available balance, not another deduction from invoice due. Use the existing manual time-entry calculation: each duration rounds up in six-minute increments (0.1 hour); automatic ingestion and held review use the same calculation. Do not introduce quarter-hour rounding.

Create Invoice, Account Audit and Accounts Receivable continue to use the latest balance snapshot of each live current statement chain. An issued parent is its original financial record, **not** a mutable current-balance cache. New payments and write-offs append snapshots; they may not mirror changes onto a locked parent. Carry-forward closes a locked chain by appending a zero-balance child with the existing `absorbed_by` marker, preserving every issued row. New work and ledger events remain eligible for the next statement. Details distinguish issued amounts from the current account/chain balance.

## 5. Flagged exception → permitted reversal → revision or roll forward (run 1)

Owner: “if theres a bounced check we need a way to flag that a specific condition was hit, like bounced check which should then unlock and allow a reverse which would allow for that invoice to be reprinted and resent or rolled into a new invoice.”

### State machine and authorization

An extensible condition registry initially exposes `bounced_check`. Each exception records invoice/customer/account, condition, required reason, session actor/time, selected payment IDs and state. Manager/admin/owner only. States: `flagged` → `reversed` → `resolved_revision` or `resolved_roll_forward`; an uncorrected flag may be cancelled with a history entry. Only one active exception per invoice is allowed to keep revision ordering unambiguous. A payment may be reversed once; retries return conflict without another money event.

The flag grants **only permission to reverse exactly the selected payments using the exception route**. It does not grant arbitrary edit/delete permission or unlock unrelated invoice items. Original receipt rows and original invoice remain unchanged. This is the narrow accounting meaning of unlock: an audited compensating positive event is allowed while the issued evidence remains immutable. After reversal the grant is consumed, and the resolution closes the workflow. Every transition stores actor, timestamp, reason, invoice, affected IDs and amounts in append-only history.

Validate all selected payments before any write: unique positive IDs, belong to this statement/customer/account, normal negative receipts, not retainer-funded/reversal/already reversed. Overpayment excess requires its associated retainer to be untouched by draws; if already used, refuse atomically with corrective guidance. Where unused excess is cancelled, append a retainer event/snapshot if the original is locked. No partial batch reversal is allowed.

### APIs

- `GET /invoices/:invoiceID/history/:accountID/:userID`: lock status, supported conditions, original/revision files, events and exceptions with selected payments.
- `POST /invoices/:invoiceID/exceptions/:accountID/:userID`: `{condition, reason, paymentIds}`; flag and record the narrow grant.
- `POST /invoices/:invoiceID/exceptions/:exceptionID/reverse/:accountID/:userID`: reverse all selected payments atomically, record positive reversal IDs and before/after balances.
- `POST /invoices/:invoiceID/exceptions/:exceptionID/resolve/:accountID/:userID`: `{action: 'revision'|'roll_forward'|'cancel'}`. Revision is allowed only while this is the current live statement; an absorbed/older invoice must roll forward. Cancellation only before reversal. Resolve with revision generates and archives the revised artifact before committing revision metadata, leaving state retryable if storage fails.
- Existing account-authorized invoice downloader reprints archived original/revision files unchanged. Download is not another ledger event and does not imply email delivery.

All new routes use actual HTTP 400 validation, 401/403 role/account, 404 missing/foreign record, 409 state/locked/conflict and 500 unexpected database/storage failure. Failed transitions leave history, exception state and money unchanged. Storage uses unique per-attempt keys; a failed DB commit may leave an unreferenced artifact, never an overwritten original or a referenced missing object.

### Balances, artifacts and UI

A reversal restores the applied amount on the current live chain exactly once using a new positive payment and a new balance snapshot. An old statement's bounced receipt also restores debt on the current chain, not on an absorbed historical chain. Roll-forward resolves the exception and leaves that restored balance for the next ordinary invoice. It does not post another charge. Revision keeps the same invoice number, increments its revision number, labels the document Revision N — bounced payment correction, lists the original amount and corrections, and preserves the original statement content/archive. The revision amount is original issued due plus the selected corrections accumulated across revisions; current outstanding is displayed separately so subsequent new receipts are not silently incorporated into issued evidence.

Invoice details shows Sent — locked, Flag exception, payment selection, condition/reason, explicit Reverse selected payments, then Reprint/resend revision or Roll into next invoice, status/errors, revision download and chronological history. Generic locked-payment reversal links direct the operator to the owning sent statement. Flags remain visibly present until resolved. Reprinting any archived version is always available.

### Integrity and money

Each account's chain is serialized with a transaction advisory lock. The central request boundary takes that lock before business-row locks to prevent a concurrent employee deletion and work insert from deadlocking; explicitly read-only snapshots do not take it. Direct SQL capture takes the same account lock. Canonical PostgreSQL JSON (UTC) hashes all event fields plus the previous SHA-256. UPDATE/DELETE/TRUNCATE and direct INSERT of chain evidence are refused; mutable business records retain their existing edit permissions and sent locks. `ds2_verify_audit(account_id)` checks every link/hash and the retained head/count, detecting changes, gaps and tail removal. Printable records retain their chain anchor. A privileged attacker rewriting the entire database including anchors requires separately retained backups/anchors to detect; this feature does not claim protection against a database superuser.

History inverts captured changes against current rows to recover the activation baseline, including deleted or moved rows. Older available rows are reconstructed with known dates and creator IDs, explicitly labelled "reconstructed from existing records, before audit logging began"; missing actor/name/edit history stays unknown. Forward replay groups all changes from each database transaction. Balances are calculated after the complete posting using the existing deterministic Account Audit arithmetic, preserving rolling latest-chain balance plus unbilled work/credits. Statement issuance is an informational marker, never another lifetime charge. Retainer availability is shown separately and is not deducted twice; draws use their actual payment, and refunds/adjustments change availability. Dates filter Phoenix posting dates; the opening balance includes earlier postings and pagination never resets the balance. New invoice drafts remain editable and write nothing to the ledger; finalize means sent and locked. Exception unlocks remain narrow compensating reversals; all transitions/revisions and reprint actions join the chain.
